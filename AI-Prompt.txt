================================================================================
 AI PROJECT PROMPT -- "PS51 Bootstrap" generic project generator (v1:
 project-agnostic, 64-bit, self-contained, external launch, standalone
 double-click-safe programs; works for console, GUI, and other program kinds).
 Paste this ENTIRE prompt into the AI. It is fully self-contained: assume the
 AI has NO prior context. This prompt is REUSABLE across many different
 projects: after pasting it, append a PROJECT DESCRIPTION of the specific
 program I want (Section 0 explains how that works). Follow-up requests may
 be appended after it; the rules below always stay in force for every project
 built from this prompt.
================================================================================

------------------------------------------------------------------------------
 SECTION 0 -- PROJECT PROFILE (what makes this prompt reusable)
------------------------------------------------------------------------------
This prompt is deliberately GENERIC: nothing in it is tied to one program,
language, or UI style. Each project built from it is described by a
"profile". When I append a PROJECT DESCRIPTION, it fills profile slots; any
slot it leaves unfilled uses the DEFAULT below. The defaults are fully
specified, so the bootstrap runs correctly even when this prompt is pasted
with no description at all.

Profile slots (DEFAULT in parentheses):
  P1  ProgramKind ......... "console" | "gui" | "other" (console).
                            "gui" = windowed app with its own UI (e.g.
                            WinForms), no console window expected.
  P2  Build toolchain ..... how sources become the artifact: build command,
                            language version, references, flags
                            (in-box csc.exe, C# 5.0, .NET Framework 4.x;
                            see Section 1 A item 4 and R2).
  P3  Project files ....... every file under src\ and its contents
                            (one placeholder Program.cs, src\App.config,
                            src\Properties\AssemblyInfo.cs).
  P4  Output artifact ..... what the build produces and where
                            (build\bin\<ProjectName>.exe).
  P5  Runtime companions .. files that MUST sit beside the artifact when it
                            runs (NONE -- the artifact runs alone).
  P6  NonInteractiveFlag .. one command-line flag that makes the program
                            perform its startup and exit BY ITSELF with
                            code 0 and zero user interaction
                            (console: --no-pause; gui: --smoke-test).
  P7  Smoke assertions .... output-content checks beyond the exit code
                            (none).

When a PROJECT DESCRIPTION is present: fill the slots from it, keep the
defaults for the rest, and STATE which slots you filled and how. If the
description conflicts with a hard rule (Section 2), resolve per M2 and say
so. For "other" kinds the description MUST define (a) how a human observes
the program's result and (b) how it self-verifies non-interactively (the P6
equivalent); if it does not, fall back to the console contract and say so.

------------------------------------------------------------------------------
 SECTION 1 -- WHAT I WANT (the exact deliverable)
------------------------------------------------------------------------------
ONE Windows PowerShell script, bootstrap.ps1 (single file), that works on a
stock 64-bit Windows machine with nothing but Windows PowerShell 5.1 and
.NET Framework 4.x, and that SCAFFOLDS a second script (run.ps1) as project
content. On every run bootstrap.ps1:

(A) BUILD + VERIFY (bootstrap.ps1 itself):
  1. Creates the project folder <BasePath>\<ProjectName>.
     -ProjectName is a script parameter (default "DemoBuild");
     -BasePath is a script parameter (default "C:\temp"). Validate
     ProjectName against invalid filename characters and abort cleanly
     (paused window) if bad.
  2. Is IDEMPOTENT: completely deletes the existing project folder and
     recreates every file and folder from scratch, so repeated runs always
     converge to an identical, clean result.
  3. Scaffolds exactly this tree (fixed skeleton plus profile P3 files):
        <ProjectName>\
            run.ps1                       <-- standalone launcher (see B)
            src\...                       <-- profile P3 project files
            build\bin\                    <-- artifact + build byproducts
            build\logs\                   <-- bootstrap.log, run.log,
                                              run-transcript.txt
            docs\README.md
            tests\README.md               <-- placeholder only
            .gitignore
  4. BUILD STEP (from profile P2/P3):
     - DEFAULT PROFILE: compile with the IN-BOX .NET Framework compiler
           %WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe
       (fall back to the non-64 path if that is missing), passing
       /platform:x64 plus /target:exe (console kinds) or /target:winexe
       (gui kinds, so no stray console window appears). GUI projects add
       whatever framework references they need (e.g.
       /r:System.Windows.Forms.dll /r:System.Drawing.dll). The compiler
       process's own bitness is IRRELEVANT to the output bitness; only
       /platform:x64 matters -- say so in a debug log line. Derive
       identifiers/namespaces from ProjectName (strip characters invalid
       in identifiers; prefix "_" if it starts with a digit).
     - 64-bit is the default target for any PE we build: abort up front
       (fatal, paused window) on 32-bit Windows, because a /platform:x64
       exe could never run there. Log OS/process bitness in DEBUG.
     - NO internet, NO installs, NO downloaded modules. ONE exception: a
       PROJECT DESCRIPTION may EXPLICITLY declare an external tool as
       present (slot P2); then the build may use it, but must probe for it
       up front and abort with a clear paused message if it is missing.
       Without such a declaration, in-box only: NO dotnet CLI, NO MSBuild,
       NO Visual Studio, NO NuGet, nothing outside the Windows inbox.
  5. 64-BIT VERIFICATION (fatal on failure) whenever the artifact is a PE
     executable we compiled (the default): parse the artifact's raw bytes
     and verify the PE header:
       - 'MZ' at offset 0
       - e_lfanew (PE offset) is the Int32 at 0x3C
       - 'PE' signature at that offset
       - machine type (UInt16 at peOffset+4) MUST equal 0x8664 (AMD64)
       - optional-header magic (UInt16 at peOffset+24) MUST equal 0x20B
         (PE32+)
     Read bytes with [System.IO.File]::ReadAllBytes -- NEVER
     Get-Content -AsByteStream (that is PowerShell 6/7-only). For non-PE
     artifacts, replace this step with the profile's declared artifact
     verification and log the substitution.
  6. SELF-CONTAINED REQUIREMENT (profile P5):
     - Default: the artifact must reference ONLY inbox components (for
       the default profile: mscorlib et al.), need ZERO files beside it
       (no DLLs, no config, no satellites, no data files), and use no
       packages, no ILMerge, no Costura, no embedding tricks.
     - DEFINITION (state it in the README too): under these constraints
       the runtime cannot be statically linked, so "self-contained"
       means: the artifact runs with nothing beside it, and its only
       runtime requirements are inbox OS components (for the default
       profile: the .NET Framework 4.x CLR, an inbox component of Windows
       10/11 -- not a file dependency). This is the maximum achievable
       without a forbidden SDK. State it honestly rather than glossing
       over it.
     - PROVE IT with an isolation test: copy ONLY the declared runtime
       set (default: the artifact ALONE) into a bare temp folder, run it
       there with the NonInteractiveFlag (P6), require exit code 0 (for
       gui kinds, enforce a timeout: kill the process and count failure
       if it does not self-exit), log its output, then delete the temp
       folder. Failure = logged error (counted, non-fatal).
     - Any staged config (e.g. exe.config) may sit beside the artifact
       but is OPTIONAL at runtime; the isolation test must demonstrate
       the artifact runs without it.
  7. Smoke-tests the artifact inline from build\bin WITH the
     NonInteractiveFlag (P6): runs it, captures stdout+stderr (may be
     empty for gui kinds), logs every line, checks the exit code, and
     applies any profile P7 assertions. For gui kinds, wait for self-exit
     with a timeout and treat a timeout as failure. This is build
     VERIFICATION only -- it is not the auto-launch and must not be
     removed.
  8. AUTO-LAUNCH HAPPENS OUTSIDE THE BUILD SCRIPT:
     - bootstrap.ps1 itself NEVER executes the program at the end.
     - run.ps1 is scaffolded as a normal project file, regenerated fresh
       on every bootstrap run, with the artifact name (P4) baked in at
       generation time.
     - Unless -NoLaunch was supplied, bootstrap.ps1 spawns a NEW Windows
       PowerShell 5.1 console window that executes run.ps1, via:
           Start-Process on (Join-Path $PSHOME 'powershell.exe') with
           -ArgumentList @('-NoProfile','-ExecutionPolicy','Bypass',
                           '-File','"<quoted path to run.ps1>"')
       and does NOT use -Wait (the app window is fully independent). A
       spawn failure is logged as an error but is never fatal; suggest
       the manual command in that case.
     - End state: the build window (paused) AND the program running --
       a console app running in the launcher window, or a gui app showing
       its window -- then paused/awaiting the user.
  9. Ends with an interactive pause (Read-Host) so the console window
     NEVER closes itself -- on success, on failure, AND on every abort
     path.

(B) run.ps1 -- the STANDALONE launcher, EMBEDDED as a template inside
    bootstrap.ps1 and written out as project content on every run:
  1. Same Windows PowerShell 5.1-only guard as bootstrap.ps1.
  2. Locates the artifact (P4) relative to its own $PSScriptRoot (embedded
     artifact name, no guessing, no scanning).
  3. Accepts passthrough arguments for the program via
     [Parameter(ValueFromRemainingArguments = $true)] and splats them.
  4. KIND-DEPENDENT invocation:
     - CONSOLE kinds: APPENDS the NonInteractiveFlag (--no-pause) to the
       program's arguments (REQUIRED, not optional) because run.ps1
       supplies the window's pause itself: one keypress total, and the
       program's exit code is logged before the pause. Runs the program
       INLINE in its own window with live output (no redirection) and
       captures the exit code ($LASTEXITCODE).
     - GUI kinds: passes the arguments straight through -- the
       NonInteractiveFlag is NEVER used on human launches -- runs the
       program INLINE, waits while the user uses the window (the
       launcher console simply waits; log that this is expected), then
       logs the exit code once the user closes the app.
  5. Logs to build\logs\run.log in the same timestamped DEBUG/INFO/WARN/
     ERROR style as bootstrap.ps1, AND records a full console transcript
     via Start-Transcript to build\logs\run-transcript.txt
     (Stop-Transcript on the way out).
  6. If the artifact is missing, logs an error telling the user to run
     bootstrap.ps1 first, then pauses and exits nonzero.
  7. Pauses with Read-Host before closing (its window never auto-closes),
     then exits with the program's exit code.
  8. Must ALSO work when run manually at any time, independent of
     bootstrap.

(C) THE PROGRAM'S STANDALONE EXECUTION BEHAVIOR (mandatory; applies to
    whatever program the profile describes). The DEFAULT program, used
    only when no PROJECT DESCRIPTION replaces it, is a minimal console
    placeholder that prints the project name plus machine/user/CLR/OS/
    64-bit-process info and takes an optional name argument. Any PROJECT
    DESCRIPTION replaces the placeholder program entirely -- but the
    behavior contract below survives the replacement:

    CONSOLE programs:
    - Double-clicking the exe in Explorer must leave the console OPEN
      until the user presses Enter. (Root cause to design against:
      Windows owns a console app's window, so it is destroyed the
      instant Main returns -- Explorer does not hold it open. A bare
      console app "flashes and closes".)
    - The exe must implement a pause-before-exit that prints something
      like "Press Enter to exit... " and calls Console.ReadLine().
    - The pause must run on BOTH the success path AND the
      unhandled-exception path (e.g., wrap Main's body in
      try/catch/finally and call the pause in the finally), so even a
      crash stays readable instead of vanishing.
    - The pause is skipped ONLY when:
        (a) the NonInteractiveFlag (--no-pause) is present in the
            command line (case-insensitive, may appear anywhere); OR
        (b) Console.IsInputRedirected is true (piped/automated stdin
            that can never supply a keypress). Console.IsInputRedirected
            is .NET 4.5+, which Windows PowerShell 5.1 itself requires,
            so it is allowed.
    - Argument parsing must strip the NonInteractiveFlag tokens; the
      remaining tokens are the program's own arguments.
    - ReadLine must be wrapped so a broken/null stdin (EOF returns null)
      can never throw on the way out.
    - ALL automated invocations pass the flag: the bootstrap smoke test
      (A item 7), the isolation test (A item 6), and run.ps1 (B item 4).
      Without the flag these steps would block forever, because their
      stdin is a console, not a redirect.

    GUI (windowed) programs:
    - Double-clicking the exe must show the program's main window and
      keep the process alive until the user closes it. The GUI analog
      of "flash and close" is a window that never appears or a process
      that dies instantly -- design against that.
    - Startup failures and unhandled exceptions must be VISIBLE, never
      silent: wrap the entry point in try/catch, wire unhandled-
      exception handlers, and surface any crash as a modal error (e.g.
      a MessageBox with the exception message) that waits for the user
      to dismiss it before the process exits.
    - The exe must support the NonInteractiveFlag (--smoke-test,
      case-insensitive, may appear anywhere): perform full startup/
      initialization (optionally showing the window briefly), then exit
      with code 0 BY ITSELF, no user interaction. The smoke test and
      isolation test (A items 6-7) use it; the launcher (B item 4) never
      does.
    - Automated runs of gui kinds must enforce a timeout: if the process
      does not self-exit within the timeout, kill it and count it as a
      failure.
    - Compile with /target:winexe so no console window appears.

    OTHER kinds: the PROJECT DESCRIPTION defines the equivalent contract
    (human-observable result + non-interactive self-verification); if it
    does not, the console contract applies.

------------------------------------------------------------------------------
 SECTION 2 -- HARD RULES (non-negotiable constraints)
------------------------------------------------------------------------------
R1. WINDOWS POWERSHELL 5.1 EXCLUSIVELY (both scripts).
    - Both scripts must REFUSE to run under PowerShell 6/7 (pwsh): check
      $PSVersionTable.PSVersion.Major -ne 5, print a clear error, pause
      with Read-Host, then exit 1.
    - Use ONLY PowerShell 5.1-compatible syntax and cmdlets. FORBIDDEN
      (PS 6/7 only): && and || pipeline chains, ?? and ??=, ternary
      (a ? b : c), ForEach-Object -Parallel, Join-Path with 3+ arguments,
      ConvertFrom-Json -AsHashtable, -Encoding utf8NoBOM, Get-Error,
      Get-Content -AsByteStream. Read binary files with
      [System.IO.File]::ReadAllBytes instead.
    - All run examples must say powershell.exe, never pwsh.
    - Two-argument Join-Path with a nested child path (e.g.
      Join-Path $root 'build\bin') IS allowed and expected.

R2. TOOLCHAIN/LANGUAGE PER PROFILE; DEFAULT = C# 5.0 / .NET FRAMEWORK 4.x.
    - Reason for the default: the in-box csc.exe supports at most C# 5;
      that is the newest version buildable on ANY stock PS 5.1 machine
      with zero installs.
    - FORBIDDEN in default-profile .cs sources: string interpolation
      ($"..."), null-conditional (?. ?[]), nameof, expression-bodied
      members (=>), auto-property initializers, inline "out var"
      declarations at the call site (classic out parameters, declared
      before the call, ARE allowed and expected for argument parsing),
      tuples/ValueTuple, pattern matching, switch expressions,
      using-declarations without braces.
    - ALLOWED: var, generics, lambdas, async/await, String.Format,
      classic { get { ... } } property blocks, classic out parameters.
    - Default-profile App.config must contain <supportedRuntime
      version="v4.0" ... />.
    - Any OTHER toolchain declared in a project description carries the
      same rule in kind: use ONLY language features the declared compiler
      version actually supports; never silently assume a newer one.

R3. SINGLE FILE DELIVERABLE, ZERO EXTERNAL DEPENDENCIES. bootstrap.ps1 is
    one file and embeds the run.ps1 template. Nothing is downloaded or
    installed.

R4. TRUE IDEMPOTENCY (bootstrap.ps1). The wipe must be robust:
    - If the console's current location is INSIDE the project folder,
      step out (Set-Location to the parent) BEFORE deleting, or deletion
      fails.
    - Recursively strip ReadOnly/Hidden/System attributes first.
    - Retry the delete up to 3 times with a short sleep between attempts.
    - Verify the folder is gone; if it is not, abort with a clear error
      and a paused window.
    - run.ps1 lives INSIDE the project folder BY DESIGN and is
      regenerated on every run -- that is expected, not a bug.

R5. VERBOSE DEBUG LOGGING ON EVERY PROCESS (both scripts).
    - Timestamped log lines with levels DEBUG / INFO / WARN / ERROR,
      color-coded in the console AND mirrored to a file:
      bootstrap.ps1 -> build\logs\bootstrap.log; run.ps1 ->
      build\logs\run.log.
    - Wrap each logical build step in an error-trapping runner that logs
      the step name, the exception message, and the script stack trace;
      steps may be fatal (abort) or non-fatal (counted, continue).
    - Echo the build tool's stdout/stderr line-by-line with a prefix,
      and check its exit code.
    - Echo the smoke test's and isolation test's captured output and
      exit codes.
    - At the end of the bootstrap, dump the most recent $Error records
      if any exist.
    - Print the final project tree with per-file sizes and folder/file
      counts.
    - CAUTION (PS 5.1 quirk): redirecting a native command's stderr with
      2>&1 while ErrorActionPreference is 'Stop' raises
      NativeCommandError. Keep ErrorActionPreference at 'Continue' (use
      per-cmdlet -ErrorAction Stop) and judge native-command success by
      exit codes instead.

R6. AUTO-LAUNCH IS EXTERNAL -- STRICT SEPARATION OF BUILD AND LAUNCH.
    - bootstrap.ps1 must NOT run the program at the end (the inline
      smoke test in Section 1 A item 7 is the only exception and stays).
    - ALL launching logic lives in run.ps1, which bootstrap.ps1
      scaffolds and (unless -NoLaunch) spawns in a separate new PS 5.1
      window without waiting on it.
    - run.ps1 must pause (Read-Host) so its window never auto-closes,
      log everything it does, and be independently runnable by hand.
    - A failed spawn is logged as a non-fatal error plus the manual
      command.

R7. NO WINDOW EVER CLOSES ITSELF -- INCLUDING THE PROGRAM'S OWN. No exit
    path in either script may skip its Read-Host pause, and the program
    itself must never exit (or vanish) while a human could still be
    reading its result: console kinds pause (R10); gui kinds keep a
    visible window or surface a visible error and wait for dismissal
    (R10).

R8. PARAMETER INTERFACE: -ProjectName, -BasePath, -NoLaunch (bootstrap);
    passthrough app args (run.ps1). Validate ProjectName against invalid
    filename characters and abort cleanly if bad.

R9. 64-BIT + SELF-CONTAINED, AS SPECIFIED IN SECTION 1 A ITEMS 4-6:
    - /platform:x64 compile (default profile); abort on 32-bit Windows;
      fatal PE-header verification (machine 0x8664 AND optional-header
      magic 0x20B) whenever the artifact is a PE we built.
    - The artifact must run standalone (isolation test) with only the
      declared runtime set (default: nothing) beside it.
    - Do NOT attempt true static linking; do NOT use ILMerge, Costura,
      AppLocal, or any single-file publish. State the "runtime is an
      inbox OS component" limitation honestly in the README.

R10. STANDALONE EXECUTION OF THE PROGRAM (see Section 1 C):
    - CONSOLE kinds: double-clicking the exe must leave its console open
      until Enter; the pause covers the success path AND the
      unhandled-exception path; the ONLY opt-outs are the
      NonInteractiveFlag and redirected stdin; every automated
      invocation (smoke test, isolation test, run.ps1) MUST pass the
      flag, or the build hangs forever. Do NOT "fix" the window flash by
      removing the pause, by launching the exe only through run.ps1, or
      by moving the pause into PowerShell -- the pause belongs INSIDE
      the program so the double-clicked binary is self-sufficient.
    - GUI kinds: double-clicking the exe must show a window and stay
      alive until the user closes it; startup/unhandled exceptions must
      surface as a visible modal error and wait for dismissal; the
      NonInteractiveFlag exists for automation only and is never used
      on human launches.
    - Never weaken either contract when adapting this prompt to a new
      project.

 SECTION 3 -- HOW THE AI MUST HANDLE THESE RULES (meta-rules)
------------------------------------------------------------------------------
M1. Treat R1-R10 as hard constraints, never suggestions. Do not trade them
    away for brevity, elegance, or "modern best practice".
M2. If a later request or project description seems to conflict with a
    rule, resolve in this priority order: (1) it must actually run
    correctly, (2) R1/R2 version compatibility, (3) everything else.
    State the conflict and your choice.
M3. NEVER silently drop, weaken, or reinterpret a requirement. If one is
    impossible as written, name it, explain why, propose the closest
    compliant alternative, and implement that alternative.
M4. Assume NOTHING exists on the machine beyond 64-bit Windows + PowerShell
    5.1 + .NET Framework 4.x, UNLESS my project description explicitly
    declares a tool present (then probe for it before use). Never
    recommend installing PowerShell 7, the .NET SDK, Visual Studio, or any
    PowerShell module.
M5. Always deliver the COMPLETE, runnable bootstrap.ps1 in ONE code block
    (with the run.ps1 template embedded inside it). No placeholders, no
    TODOs, no "...rest unchanged..." elisions. A short explanation of
    decisions may accompany the code.
M6. Before delivering, self-audit against the Section 4 checklist and fix
    every violation found. State anything you could not satisfy.
M7. When I later request changes to the program itself (new files,
    features, even a different program kind), put sources under src\, add
    them to the build's source list, keep the output at P4 as a 64-bit
    self-contained artifact, PRESERVE the standalone behavior and
    NonInteractiveFlag contract exactly, and keep every rule intact.
    run.ps1 keeps working unchanged as long as the artifact stays at P4.
M8. If I ever store bootstrap.ps1 INSIDE the project folder, warn me that
    the idempotent wipe will delete it; it belongs outside (e.g. C:\temp).
    run.ps1 inside the project is correct and expected.
M9. Never merge the launcher back into bootstrap.ps1, and never make
    bootstrap.ps1 execute the program at the end, even if it seems
    simpler -- build and launch must remain two separate
    scripts/processes.
M10. Never "solve" self-containment by recommending dotnet publish,
     single-file bundles, NativeAOT, ILMerge, or trimming -- all violate
     the no-SDK default. The accepted model is: artifact + zero companion
     files (unless the profile declares them) + runtime as an inbox OS
     component, and it must be stated honestly rather than glossed over.
M11. Never "solve" a vanishing window by removing or weakening the
     program's built-in standalone behavior (R10). If a future change
     seems to require the program to exit immediately in some context,
     implement it as an explicit NonInteractiveFlag opt-out at the
     command line, never as removal of the default behavior.
M12. PROFILE DISCIPLINE: when my appended project description exists, fill
     the Section 0 slots from it, keep defaults for the rest, and state
     which slots you filled and how. Never invent project requirements I
     did not state, and never let the default placeholder program leak
     into a project I actually described.

 SECTION 5 -- HOW I WILL RUN IT (sanity tests)
------------------------------------------------------------------------------
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -ProjectName MyTool
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -NoLaunch
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run.ps1 [app args]

  Manual program tests (adjust per ProgramKind):
  - Console: double-click build\bin\<ProjectName>.exe in Explorer ->
    console appears, prints output, shows "Press Enter to exit...", and
    stays open until I press Enter. It must NOT flash-and-close.
  - Console, from a console: .\build\bin\<ProjectName>.exe --no-pause
    -> prints output and exits IMMEDIATELY (no pause).
  - Console, piped: "input" | .\build\bin\<ProjectName>.exe
    -> stdin is redirected, so no pause; exits immediately.
  - GUI: double-click build\bin\<ProjectName>.exe -> the program's window
    appears and stays open until I close it.
  - GUI, from a console: .\build\bin\<ProjectName>.exe --smoke-test
    -> initializes, then exits 0 BY ITSELF (no interaction, no lingering
    window).

  Expected overall: the build run pauses at the end; unless -NoLaunch, a
  second window opens running the program via run.ps1 (console kinds: the
  flag is passed and the launcher pauses once itself; gui kinds: the app
  runs until I close its window, then the launcher logs the exit code and
  pauses once); reruns rebuild cleanly from scratch; run.ps1 works by hand
  anytime; the build log shows the 64-bit PE verification (for PE
  artifacts) and the isolation test passing.
